1 Why there is a database at all

The first version of this project was a script. Fetch, embed, summarise, print, exit. Everything it learned died when the process did.

Adding SQLite changed what kind of thing the project is. Run the script twice and it does the same work twice. Run the system twice and the second run is mostly free, because the first run left something behind.

Three things now survive between runs:

articles
You have seen this URL before. Don't store it twice.
embeddings
You have already turned this exact text into a vector. Don't pay the model again.
summaries
You have already asked the LLM about this article, for this goal, with this model. Don't ask again.
The idea, named

This is compounding state. Each run leaves the system better positioned for the next one. It is the difference between an "LLM wrapper" and a system — a wrapper re-derives everything from scratch on every request; a system remembers.

You wrote this in your own project philosophy before you built it. The DB is that sentence turned into code.

Two of those three are caches. A cache is any store where the answer is expensive to compute and cheap to look up, and where the same input always gives the same answer. That last part matters — it's what makes a cache safe. Change the input and you must get a different cache entry, never a stale one. Section 4 shows the trick that guarantees it.

Read the shape, not the columns

Four tables have exactly the same two foreign keys: article_id and goal_id. That repetition is the design telling you something.

The unit of work in this system is not an article. It is an (article, goal) pair. One article seen through two goals is two different things — two scores, two summaries, two opinions. The schema already believes this. The pipeline code doesn't yet.

3 Keys and constraints — where the logic actually lives

The most important behaviour in this codebase is not written in Python. It is written in CREATE TABLE.

UNIQUE is not documentation

Look at how deduplication works. There is no if url in seen: anywhere. Instead:

Backend/src/storage/db.py · line 27
url_hash TEXT NOT NULL UNIQUE

That one word makes duplicates impossible, not just unlikely. SQLite refuses the insert and raises. Your Python then translates that refusal into a return value.

Why this is the right place for it

A Python check can be bypassed — by a second process, by a future route you write, by a script you run by hand at 2am. A constraint cannot. It sits under every path into the table.

Named: this is an invariant — a statement that is true about your data at all times, no matter what code runs. Push invariants down to the lowest layer that can enforce them.

Composite primary keys

embeddings has no id. Its key is two columns together:

Backend/src/storage/db.py · line 42
PRIMARY KEY (text_hash, model_name)

Neither column alone is unique. The same text embedded by two models is two legitimate rows. The same model embedding two texts is two legitimate rows. Only the combination must be unique.

Why model_name is in the key

A vector from MiniLM and a vector from Gemini live in different mathematical spaces. Cosine similarity between them is not "a bit wrong" — it is meaningless. A number comes out, it looks fine, and it means nothing.

Putting model_name in the key makes that mistake unrepresentable. Two models can never collide into one row. When you swap to a hosted embedding API for deployment, your old 384-dim vectors simply stop being looked up. Nothing corrupts.

Same reasoning applies to summaries. Change the LLM, get a new cache entry, keep the old one for comparison.

PRAGMA foreign_keys = ON

Backend/src/storage/db.py · lines 13–18
def _connect():
    conn = sqlite3.connect(DB_PATH)
    conn.execute("PRAGMA foreign_keys = ON")
    return conn

SQLite ignores FOREIGN KEY declarations unless you turn enforcement on, per connection. Not per database, per file, or once at setup — every single connection.

Without that line, every FOREIGN KEY in your schema is a comment. You could insert a similarity row pointing at article 99999 and SQLite would accept it happily.

Why the private function matters

The underscore in _connect means "internal to this module". It exists so the pragma can never be forgotten. If every function called sqlite3.connect() directly, the rule would live in fourteen places and one of them would eventually miss it.

Named: a single choke point. Any rule that must apply everywhere should have exactly one place it can be written.

4 Hashing — how identity works here

Two different hashes do two different jobs. Both turn "is this the same thing?" from a hard question into a string comparison.

url_hash — same article, different link

These four URLs are one article:

raw url
https://WWW.Example.com/a?utm_source=x&id=7#top
Mixed case host, tracking param, real param, fragment.
normalize_url
https://example.com/a?id=7
force https · lowercase host · strip www. · drop utm_* and friends · drop #fragment · keep real params
sha256
4f2a9c…
Fixed 64 chars whatever the input length.
UNIQUE column
articles.url_hash
Second insert raises IntegrityError.
The judgement call inside normalize_url

?id=7 is kept, ?utm_source=x is dropped. Both are query params — the code has to know which ones change what page you get.

That knowledge is a hardcoded set in url_help.py, and your own comment says #gotta look here. You are right to flag it. Get it wrong in one direction and you store the same article twice; wrong in the other and you silently drop a real article because it collided with a different one.

There is no clever fix. It is a list you extend when reality surprises you. Most production systems have exactly this list.

text_hash — content-addressed caching

Same idea, different purpose. The vector cache is keyed by sha256(text), so:

  • Same text → same hash → cache hit, no model call.
  • One character changes → completely different hash → cache miss, fresh embedding.

Nothing invalidates this cache. There is no expiry, no version bump, no "clear cache" button. Correctness is automatic because the key is the content.

Named: content-addressed storage

Git works this way. Docker layers work this way. IPFS works this way. Address a thing by the hash of what's inside it, and the question "is my cached copy stale?" stops existing — a changed thing simply has a different address.

The trade-off: you can never look up "the vector for goal 3". You can only look up "the vector for this exact string". Edit the goal text and the old vector is still sitting there, correct but orphaned. That is the price, and here it is worth paying.

One consequence worth seeing: embeddings has 91 rows for 90 articles. Ninety article embeddings, plus one goal embedding. The goal was embedded once and read from cache for the other 89 articles.

5 Every function, what it returns, what it catches

Thirteen functions in db.py. The return value is the interesting column — several of them encode a fact you can't get any other way.

FunctionKindReturnsCatchesWhat the return value tells you
_connect() helper Connection — Every connection in the codebase comes from here, so FK enforcement is always on.
init_db() write None — Seven CREATE TABLE IF NOT EXISTS. Safe to call on every run. See section 9 for what it can't do.
insert_article(...) write int | None IntegrityError The dedup signal. An int means brand new, and it's the id. None means this URL was already stored.
update_article_content(url, content) write bool — cur.rowcount > 0 — did any row actually match? False means the URL isn't in the table.
get_article_content(url) read str | None — Ambiguous on purpose: None means either "no such article" or "article exists, body not fetched yet".
get_embedding(text, model) read ndarray | None — Cache hit or miss. Rebuilds the float32 array with np.frombuffer.
save_embedding(text, vec, model) write None INSERT OR IGNORE Nothing. Idempotent — calling it twice is harmless and silent.
insert_goal(text) write int — New goal id. No uniqueness check — the same text twice makes two goals.
get_active_goals() read list[tuple] — [(id, text), ...] where superseded_by IS NULL. Tuples, so callers index by number — see section 9.
insert_similarity(a_id, g_id, score) write bool IntegrityError True = new score stored. False = this pair was already scored.
get_summary(a_id, g_id, model) read str | None — The function that should be saving you LLM calls. Currently written, currently never called.
insert_summary(...) write None INSERT OR IGNORE Nothing. Note the inconsistency with insert_similarity — same problem, different solution.
get_pending_summary_pairs(t=0.28) read list[tuple] — Pairs that scored well but have no summary — retry candidates after a crash.
clear_pipeline_data() dev None — Wipes 4 tables, keeps goals and schema. Delete order respects FKs.
Return values are a contract

insert_article returning int | None is doing real work. It answers "did I insert?" without a second query. The alternative — SELECT first, then INSERT — is two round trips and has a race: another process could insert between your check and your write.

Named: "ask forgiveness, not permission" (EAFP). Try the operation, catch the specific failure. In Python this is idiomatic; with databases it is also the only version that is actually correct under concurrency.

Two spellings of the same idea

Look at these side by side.

insert_similarity — try/except
try:
    conn.execute("INSERT INTO similarity ...")
    conn.commit()
    return True
except sqlite3.IntegrityError:
    return False       # caller learns it was a duplicate
insert_summary — INSERT OR IGNORE
conn.execute("INSERT OR IGNORE INTO summaries ...")
conn.commit()
# caller learns nothing

Both prevent duplicate rows. The difference is who finds out. INSERT OR IGNORE is quieter and shorter; it also throws away information. If you ever want to log "skipped 12 summaries that already existed", the second version cannot tell you.

Not a bug — a decision to make once

Neither is wrong. What's worth avoiding is having both in one file for no stated reason, because the next reader (you, in October) will wonder whether the difference is meaningful.

Pick one as the house style. My suggestion: INSERT OR IGNORE when the caller genuinely doesn't care, try/except when the duplicate is information. By that rule insert_summary should probably return a bool too — "was this a cache hit?" is exactly the thing you'll want to count later.

6 Error handling — what is caught and what is deliberately not

Exactly one exception type is caught in the entire storage layer: sqlite3.IntegrityError. Everything else is allowed to crash. That is a policy, not an oversight.

The one thing that's caught

IntegrityError fires when a write violates a constraint — a duplicate url_hash, a duplicate (article_id, goal_id). It is caught in exactly two places, and in both it is translated into a return value.

Catching vs swallowing

The test is simple. After the except block runs, does the caller know what happened?

Catching: except IntegrityError: return None — the caller gets a clear answer and decides what to do. Information preserved.

Swallowing: except: pass — the failure vanishes. The caller proceeds as if it worked. Information destroyed.

Same syntax, opposite engineering.

What is not caught, and why

  • Disk full, DB locked, corrupt file — sqlite3.OperationalError. There is no sensible recovery inside a storage helper. Returning None would make "the disk is full" look identical to "not found".
  • Programming errors — wrong column name, wrong argument count. You want the traceback immediately, on your machine, not a quiet None six months later.
  • Ollama failures — crash loudly, by convention. Dedup makes re-runs cheap, so visibility beats coverage.
  • newspaper3k failures — the one exception. Caught in filter_logic.py, returns None, article is skipped for summarising. Sensible: a paywalled page is normal, not exceptional.
The convention that is about to expire

"Crash loudly" is correct while you are the only user running a script by hand. A traceback is feedback.

The moment a professor is holding the phone, the same crash is a white error page and a dead demo. The right behaviour flips: show the ranked list, fall back to the article description where a summary failed, log the error, keep going.

Your CLAUDE.md already says to revisit this at Tier 1. This is that moment. It isn't a contradiction — the correct error policy depends on who is watching.

try / finally, and why every function has it

the pattern, repeated 11 times
conn = _connect()
try:
    row = conn.execute(...).fetchone()
finally:
    conn.close()          # runs even if execute() raised
return row[0] if row else None

finally runs no matter how the block exits — normal return, exception, anything. Without it, an exception mid-query leaks the connection: the file handle stays open, and on Windows a leaked SQLite handle can lock the database file for other processes.

The shorter version you'll meet

Python has a built-in for "always clean up": the context manager, spelled with.

Careful though — with sqlite3.connect(...) as conn: does not close the connection. For sqlite3 it manages the transaction (commit on success, rollback on exception) and leaves the connection open. That surprises almost everyone once.

closing() from contextlib is the one that closes. Worth knowing the distinction exists; not worth refactoring 11 working functions today.

    8 Patterns in here worth being able to name
    
  
    Five ideas from this codebase that show up everywhere else in software. Now that you've felt them, here are the words.
    

  
    Append-only history / soft delete
    
  
    Editing a goal does not UPDATE goals SET text = .... It inserts a new row and points the old one at it via superseded_by. Nothing is ever destroyed.
    

  
    
    Why the harder way is right
    
    Suppose you overwrote the text instead. Goal 3 currently reads "learn Rust". Your similarity table has 400 rows pointing at goal 3 — all scored against "learn Rust". You edit it to "learn Go". Now 400 stored scores claim to describe a goal whose text they never saw. The data is silently, permanently wrong.
    
    
    Append-only keeps (text, embedding, score) consistent forever. Old rows point at old goals, which still exist and still say what they said.
    
    
    The cost: the table only grows, and every read must remember WHERE superseded_by IS NULL. Forget that filter once and you show the user a deleted goal. This is why the filter lives inside get_active_goals() and not at call sites — one choke point again.
    
    
    Same idea, bigger name: event sourcing. Store what happened, derive current state. Your interactions and watched tables are designed the same way — latest row per pair wins.
    
  
    

  
    The anti-join
    
  
    get_pending_summary_pairs · db.py lines 269–276
    

    SELECT s.article_id, s.goal_id, s.score
FROM similarity s
LEFT JOIN summaries sum
    ON sum.article_id = s.article_id
   AND sum.goal_id   = s.goal_id
WHERE s.score >= ? AND sum.id IS NULL
    

  
    LEFT JOIN keeps every row from the left table, filling the right side with NULL when nothing matches. So WHERE sum.id IS NULL means "the join found nothing" — rows scored high but never summarised.
    

  
    This is the SQL way to say "in A but not in B". It reads strangely the first time and then you see it everywhere: find users with no orders, articles with no summary, tasks with no owner.
    

  
    
    A real bug in this query
    
    summaries is unique on (article_id, goal_id, model_name) — three columns. This join matches on two. Switch from llama3.1:8b to Gemini and every pair still counts as "already summarised", because a row exists for some model.
    
    
    It should join on model_name too. This will bite exactly when you swap models for deployment — which is next week.
    
  
    

  
    Cache key granularity
    
  
    Three caches, three different keys, and each key is a claim about what makes an answer valid:
    
  
    
    
    embeddings
    (text_hash, model_name) — the vector depends on the text and the model. Nothing else.
    
    
    summaries
    (article_id, goal_id, model_name) — the summary depends on the article, the goal it's written for, and the model. Drop goal_id and every goal gets the same generic summary.
    
    
    articles.content
    url_hash — the body depends only on the URL.
    
  
    
  
    Getting a key wrong in either direction has a cost. Too narrow → stale wrong answers served forever. Too wide → cache never hits, you pay full price every time.
    

  
    Idempotence
    
  
    An operation is idempotent if doing it twice equals doing it once. init_db(), save_embedding(), insert_summary() all are.
    
  
    This is what lets you re-run the pipeline after a crash without thinking. Non-idempotent writes force you to track exactly how far you got before it died — which is a much harder program to write.
    

  
    Layering
    
  
    No SQL string exists outside src/storage/. filter_logic.py calls insert_article(...) and has no idea whether it's SQLite, Postgres, or a text file.
    
  
    The payoff is concrete and close: when you migrate to Postgres, you rewrite one folder. Every caller keeps working, untouched — because they were never allowed to know.
    

    

    



    

    
  
    9 Five things that will bite you
    
  
    Found while reading the code and querying your actual news.db. Ordered by how soon each one matters.
    

  
    1 · Two tables exist in code but not in your database
    

    $ SELECT COUNT(*) FROM interactions
sqlite3.OperationalError: no such table: interactions
    

  
    init_db() declares interactions and watched. news.db does not have them. You added them to the function after the database file already existed, and init_db() has not run since — or ran against a different working directory.
    

  
    
    Why CREATE TABLE IF NOT EXISTS is not a migration system
    
    IF NOT EXISTS creates a missing table. It can do nothing about a table that already exists but has the wrong shape.
    
    
    Concretely, your next task: add owner_token to goals. You'll add the column to init_db(), run it, and get no error and no column — because goals already exists, so the whole statement is skipped. Then every query mentioning owner_token fails and the CREATE looks fine, so you'll debug the wrong file.
    
    
    Real systems keep an ordered list of ALTER TABLE steps plus a record of which have run — that is what Alembic and Django migrations are. You don't need one yet. You do need to know that init_db() only ever handles a fresh database, and existing databases need ALTER TABLE by hand.
    
    
    Fix right now: run init_db() from Backend/ so the missing two get created. And note DB_PATH = Path("news.db") is relative to your working directory — run from the wrong folder and SQLite silently creates a brand new empty database instead of telling you anything is wrong.
    
  
    

  
    2 · The duplicate skip throws away work that was never done
    
  
    Backend/src/core/filter_logic.py · lines 53–63
    

    article_id = insert_article(...)
if not article_id:
    skipped_count += 1
    continue          # skips scoring AND the returned list
    

  
    insert_article returns None for an article already in the table. That is an article-level fact. But continue skips scoring and summarising, which are pair-level work that may never have happened for this goal.
    

  
    Concretely: a professor types a goal, NewsAPI returns an article you stored last week for a different goal, and it silently disappears from his results. On a fresh demo account this could empty the page completely.
    

  
    The check and the thing it guards are at different levels. The right question is "does a summary exist for this (article, goal, model)?" — and get_summary() already answers it. You need get_article_id(url) in db.py to get the id back for an article that already exists.
    

  
    3 · N+1 queries in the article loop
    
  
    Backend/src/core/filter_logic.py · line 68
    

    for i, article in enumerate(raw_articles):     # 30 times
    ...
    for goal in get_active_goals():           # opens SQLite. every. single. time.
    

  
    The goals do not change during the run. You query them 30 times to get the same answer 30 times. Hoist the call above the loop — one line moved.
    

  
    
    Named: the N+1 query problem
    
    One query to get a list, then N more queries inside the loop over it. It is the single most common performance bug in application code, and it is invisible in development — 30 fast queries feel like nothing.
    
    
    It shows up in production as "the page got slow after we got users", because N grew. Learn to spot the shape: a database call inside a loop. Sometimes it's necessary. Usually it means you should have fetched everything up front.
    
  
    

  
    4 · Tuple indexing makes the code unreadable
    
  
    Backend/src/core/filter_logic.py · lines 69, 78, 86
    

    goal_embedding = get_or_compute_embedding(goal[1])
insert_similarity(article_id=article_id, goal_id=goal[0], score=sim)
summary = summarise_test(goal[1], content)
    

  
    goal[0] and goal[1] tell a reader nothing. Add a column to that SELECT in the wrong position and every index silently shifts — no error, wrong data.
    

  
    Two fixes, both small. Unpack at the top of the loop: for goal_id, goal_text in get_active_goals(): — zero cost, immediate readability. Or set conn.row_factory = sqlite3.Row in _connect() and get goal["text"] everywhere.
    

  
    
    When positional access is fine
    
    Inside a single short function where the tuple is created and consumed three lines apart, indexes are fine. It stops being fine when the tuple crosses a function boundary — the producer and consumer can now disagree, and nothing checks.
    
  
    

  
    5 · One connection per call meets a web server
    
  
    _connect() opens a fresh SQLite connection for every function call and closes it at the end. Simple, correct, and perfectly good for a script.
    

  
    Two things change under FastAPI:
    
  
      
    
    • Concurrency. SQLite allows many readers but only one writer at a time. Two requests writing at once and the second gets database is locked. Mostly fixable with PRAGMA journal_mode=WAL, which lets readers continue during a write.
      • 
    
    • Threads. SQLite connections are not safe to share across threads, and FastAPI runs sync route handlers in a thread pool. Connection-per-call actually protects you here, since each call gets its own — accidentally the right design.
      • 
  
    

  
    
    Not a thing to fix now
    
    Your write load is one pipeline run at a time. Reads are tiny. This design will hold through the demo and well past it.
    
    
    It's here so that when you eventually see database is locked, you recognise it in ten seconds instead of an hour. That is most of what knowing a system is worth.
